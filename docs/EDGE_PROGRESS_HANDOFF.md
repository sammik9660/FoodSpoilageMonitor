# ESP32-S3 food progression handoff (local preparation only)

The existing v2.0.29 gateway already runs six-food GAS centroid classification and per-STO GAS anomaly inference on the ESP32-S3. The food candidate shown in the user's 2026-11-17 dashboard screenshot is an ESP result, not a browser model. The weak-label progression model from the prior cycle was placed in `FoodProgressModel.gs` so it could use backdated placement times and heater-off `EnvironmentHistory` without reflashing a live recording gateway. That was a demonstration shortcut. The selected model A and the time-only model had the same assumed-label holdout result as model B; no GAS improvement was measured.

`AiProgress.h` now contains the same generated time-only coefficients as `FoodProgressModel.gs`. A future gateway image can read the canonical `food_code` and user `placed_at` from the existing authenticated cloud ACK's `storage_session`, compute a seven-feature scalar logistic score locally, and report `food_progress` in health. `FoodReview.gs` prefers a fresh edge result with matching STO, sensor, food and placement time; the cloud model remains a fallback for the installed v2.0.29 gateway. Past Sheets rows, duration rules, and backdated temperature summaries still reside in Apps Script. They are not transmitted as raw records to the ESP.

This is a tiny scalar linear model. [Espressif documents ESP32-S3 SIMD-capable memory](https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/mem_alloc.html) and a separate [ESP-NN library with optimized kernels](https://github.com/espressif/esp-nn), but adding that runtime for seven scalar features would add complexity without an established speed benefit. The existing food centroid and GAS anomaly computations are also small CPU calculations. Host C++ vectors match the exported Python coefficients. The first sandbox Arduino build failed with a Windows toolchain DLL relocation error, and an unsandboxed attempt was stopped after no compiler objects appeared. A later direct unsandboxed Arduino CLI compile completed successfully with the existing 16MB/custom/OPI settings: local test BIN 1,667,856 bytes; the build's custom partition CSV hash matches the sketch source. **No on-device latency, heap impact or long-run TLS/BLE coexistence is claimed.** This binary keeps the source's existing version/build identity, is not a signed release package, and must not be installed as-is. There was no device upload or publication.

The user's screenshot has recent cloud contact, an active named food, and 120 hours of elapsed storage; local `FoodProgress.gs` produces a time-only result from those fields even when temperature coverage is poor. `FoodReview.gs` now returns a specific reason if the Apps Script runtime or coefficient file is missing, and includes a clearly marked median-exposure-duration fallback in that case. The time-only path also continues across a temporary cloud-contact gap, while the measurement freshness is displayed separately. Thus food and placement time produce a provisional stage before the first complete GAS scan and even while STO is PENDING. The operating project file list and deployed version have not been inspected, so omitted `FoodProgress.gs`/`FoodProgressModel.gs` is a strong inference, not a confirmed deployment fact.
