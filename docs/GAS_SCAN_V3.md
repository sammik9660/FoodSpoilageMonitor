## Bosch basis and units

The BME688 uses a heated metal-oxide gas sensor. Changing heater temperature changes the gas response; a series of resistances is a candidate fingerprint, not a calibrated compound concentration. [Bosch's BME688 datasheet](https://www.bosch-sensortec.com/media/boschsensortec/downloads/datasheets/bst-bme688-ds000.pdf), [product overview](https://www.bosch-sensortec.com/en/products/environmental-sensors/gas-sensors/bme688/) and [AI-Studio introduction](https://www.bosch-sensortec.com/software/bme/docs/overview/introduction.html) describe temperature cycling. The official [Bosch Arduino parallel-mode example](https://github.com/boschsensortec/Bosch-BME68x-Library/blob/master/examples/parallel_mode/parallel_mode.ino) supplies `320,100,100,100,200,200,200,320,320,320` °C and gas-wait multipliers `5,2,10,30,5,5,5,5,5,5`. It computes `sharedHeatrDur = 140 - getMeasDur(PARALLEL_MODE)/1000` **in milliseconds**, then calls `setHeaterProf(temperatures, multipliers, sharedHeatrDur, 10)` and `setOpMode(PARALLEL_MODE)`. Sequential mode uses an entirely different duration array in milliseconds; do not substitute the nominal 700/280/1400/4200 ms numbers into the parallel API.

The repository vendors Bosch's `BME68x Sensor library` **1.3.40408**, source commit `4f37df69dde205e4f58d2bb9a45568c61e128e86`, inside `firmware/nrf52840/bme688_node/src/Bosch-BME68x-Library` with its BSD-3-Clause license. The entire nRF sketch folder can be copied to another computer; Bosch does not need separate Arduino library installation. Build with `arduino-cli compile --fqbn adafruit:nrf52:feather52840 firmware/nrf52840/bme688_node` after installing the board core and OLED libraries. The wrapper calls Bosch's Sensor API. Its `bme68xData` contains compensated T (°C), H (%RH), P (Pa), G (Ω), `gas_index` (heater profile slot), `meas_index` (8-bit measurement order), and `status` (`NEW_DATA=0x80`, `GASM_VALID=0x20`, `HEAT_STAB=0x10`). Gas is divided by 1000 for the existing kΩ wire/cloud unit; pressure is divided by 100 for hPa. Bosch also provides `idac`, `res_heat`, and `gas_wait`, but v3 does not transmit them. The custom raw step data can be collected without AI-Studio/BSEC; it is not Bosch `.bmerawdata` and does not imply BSEC-derived IAQ/classification.

The Bosch example polls every 140 ms. The multiplier sum is 77; `77 × 140 ms ≈ 10.78 s` is a **nominal profile time-base estimate**, consistent with Bosch's roughly 10.8 s standard scan specification, not a measured scan period or guaranteed throughput on this board. TPH conversion, radio blocking, I²C, scheduling, and sensor timing must be measured on the actual nRF board. The 2-second fixed-heater cadence no longer applies. HP-354 is an initial reference profile, not a proven optimum for food spoilage. RDC-5-10 duty cycling is outside this version.

## Sensor and BLE wire format

On each 140 ms poll the Bosch wrapper may yield 0–3 fields. Zero new fields is normal. **Parallel mode intentionally performs dummy TPHG conversions while holding a heater step**; `GASM_VALID=0` identifies a dummy rather than a failed gas measurement. The datasheet's example repeats gas index 1 while the sub-measurement index increments. The node skips these dummy fields without failure/scan counters. A 20-second no-**real-gas-result** watchdog checks for a persistent stall. The node keeps the existing D21/D20 I²C map, address 0x76, OLED and NUS 20-byte chunk/newline/retry path. A real gas field becomes a sample only if Bosch reports all three status bits, T/H/P/G are finite, and G > 0. Invalid real gas fields are missing samples; they do not increment the frame sequence and cannot display stale T/H/P/G as current values. Three consecutive numeric/driver failures enter the existing soft-reset, reinitialization, profile reapplication and 5–60 s backoff path. Heater instability alone has a 20-second initialization grace period, to avoid treating normal warm-up as an immediate fault. The exact earlier failure cause remains unproven.

One valid heater step is one logical BLE frame, fragmented into ≤20-byte NUS writes:

```text
V=3,BID=1234ABCD,SEQ=11,SCAN=2,STEP=3,GI=3,MI=44,MS=123456,ST=176,PID=354,T=25.10,H=50.20,P=1005.30,G=84.20\n
```

`BID` discriminates nRF boots; `SEQ` counts valid transmitted step records and is separate from `SCAN`; `SCAN` increments at observed real-gas step 0 and survives sensor recovery within a boot; `STEP`/`GI` are the Bosch `gas_index`; `MI` is the Bosch 8-bit `meas_index`; `MS` is nRF uptime when the field was fetched, **not an independently calibrated sensor acquisition clock**. `ST` is the raw Bosch status byte, decimal. `PID=354` identifies the profile. T/H/P/G are °C/%RH/hPa/kΩ. An incomplete startup fragment before the first observed step 0 is discarded. A reset or missed/invalid step leaves a visible gap; no value is filled in. The constructed widest allowed frame is **139 ASCII characters / seven 20-byte payload chunks**, under the nRF 180-byte buffer and ESP 200-byte framer limit in the host parser test. BLE disconnect still loses unsent nRF data; a later SEQ/SCAN gap reveals it.

For ML, reconstruct by `(nrf_boot, scan_seq, profile_id)` **within a recording session**. Call a fingerprint complete only if exactly one row exists for every `heater_step=gas_index=0..9`, each row has the required status flags and positive finite G, and `meas_index` moves forward modulo 256 in step order. It generally **does not increase by one** between gas results, because it also counts dummy TPHG conversions. If any step is missing, repeated, out of order, or crosses a session boundary, label the group incomplete and exclude it from complete-scan ML inputs. Do not infer completeness from `STEP=9` alone. `sample_uid` deduplication happens before reconstruction. The cloud stores valid raw step rows; the grouping rule is intentionally applied downstream rather than rewriting earlier rows when later steps arrive. `python analysis/fingerprints.py PAGE.csv [MORE_PAGES.csv ...]` reports complete/incomplete groups from exported source-row pages; it does not train a model or create spoilage labels.

## Gateway, spool and cloud migration

ESP accepts strict v2 fixed-heater frames and strict v3 step frames. Every accepted frame gets its original gateway UID once. v3 uploads may contain both `sample_schema=2` legacy rows and `sample_schema=3` step rows. A v2 row remains labeled legacy and never receives synthetic heater steps. The v3 JSON fields add `scan_seq`, `heater_step`, `gas_index`, `meas_index`, `sensor_status`, `gas_valid`, `heater_stable`, `measurement_valid`, `profile_id`. Cloud accepts both upload version 2 and 3 and answers with the matching version; the new gateway requires a version 3 exact application ACK with every UID and allowed status before releasing data. The old gateway can continue using version 2 while cloud is upgraded first.

Existing SPIFFS v2 records remain **88-byte `LegacySample` files** with magic `FSM2`, version 2 and per-record CRC. New files use **120-byte `Sample`**, magic `FSM3`, version 3 and CRC. The gateway validates both formats before replay, promotes v2 only in RAM, keeps original gateway boot/rx UID and capture time, and does not rewrite or remove the old file before ACK. Mixed v2/v3 files replay in filename FIFO. Mount uses `SPIFFS.begin(false)`; a mount or CRC fault never formats the partition or calls a damaged chunk successfully replayed. A valid `.tmp` is recovered by rename; a torn file remains evidence and latches fault. Inspect `BOOT ... SPOOL pending/fault` on the real device before upgrade and back up the SPIFFS partition if it holds irreplaceable unacknowledged samples. **Do not use Erase All Flash.** An empty/unformatted device may require separately approved filesystem preparation; an apparent mount failure is not proof it is empty.

The partition menu says “1MB SPIFFS”; the earlier installed core's partition file allocated 0xE0000 = 896 KiB. The active core version/actual `SPIFFS.totalBytes()` must be read from the target boot log. At 120 bytes/step plus 16-byte header per chunk, one 32-step file costs 3,856 bytes; 128 full files hold at most **4,096 steps / 409 complete scans**, 493,568 payload bytes, before the stricter 60%-of-actual-capacity and 75%-used checks. At the unverified 10.78 s/scan nominal cadence, 4,096 steps correspond to roughly 74 minutes, **not a retention guarantee**. RAM queue is 128×120=15,360 bytes, plus 32×120=3,840 bytes each for active/staging/worker copies, JSON/TLS/task heap, and filesystem overhead. Full or corrupt storage never overwrites old data; new arrivals can be rejected with an explicit drop count when all RAM space is consumed. Power loss can still lose volatile samples before flush.

Sheets retain the first 12 `SensorData` columns and old rows. Ten v3 columns append at the right: `sample_schema, scan_seq, heater_step, gas_index, meas_index, sensor_status, gas_valid, heater_stable, measurement_valid, profile_id`. `Unassigned` uses the same extension. Legacy rows have schema 2 and blank heater metadata. An old pending **12-column** write-ahead journal is padded on recovery before comparing/writing; the reserved row/UID remains unchanged. `Sessions` and `IngestState` retain their structure. Recording assignment still uses capture time; unknown-time data goes to `Unassigned`. All Data/Current Session/Latest Session CSV and the 10,000-source-row page limit remain. CSV carries the step columns for reconstruction. No old SensorData row is deleted or reclassified.

A constructed 32-record v3 request with maximum-width IDs/numbers and health occupies about **12,910 JSON characters**, below the current 64,000-character Apps Script request guard and 45,000-character pending-journal guard in host tests. Actual TLS/heap headroom and Apps Script execution time need device/cloud validation.

## Cloud latency and rollout

The reported five-minute dashboard delay has **no proven root cause**. Prior logs show POST read timeout, 5/10/20 s retry delays, and eventual POST 302 → redirect GET 200 → valid ACK; backoff could amplify a temporary outage but is not confirmed as this event's cause. The gateway now logs uptime at boot, Wi-Fi/BLE connection, first valid frame, POST start/result and elapsed time, redirect GET start/result and elapsed time, application ACK, and backlog drain. Dashboard shows transport freshness separately from BLE and last known cloud ACK age. Ordinary retry wait caps at 30 s; HTTP 429/503 use a conservative 150 s wait. A quota error delivered as an HTTP 200 application error is not yet classified as 429/503. HTTP connect/read timeouts are separate, so 30 s is **not** an end-to-end recovery promise. Jobs remain serialized and retries preserve UIDs. TLS `setInsecure()` and current endpoint/AP configuration are unchanged prototype debts.
