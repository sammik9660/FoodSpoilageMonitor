# Environment telemetry and periodic HP-354 scans (working tree)

The mode and protocol details below describe the current code. On 2026-10-12 the user reported successful SPIFFS mount, BLE gas transfer, server storage, dashboard display, and session CSV with ESP32-S3 Flash Size 16MB / Huge APP. This report is distinct from the local builds and mock tests; long-run endurance is not established. Preserve existing rows, deployed endpoints, and unacknowledged SPIFFS files.

## Sensor schedule and failure policy

- The nRF takes heater-off forced-mode T/H/P measurements every 2,000 ms (start-to-start). A forced result needs `NEW_DATA` and finite/in-range T/H/P; the current code does not reject a repeated 8-bit measurement index. A failed conversion is a missing sample. The bundled Bosch wrapper provides `setOpMode()`, `getMeasDur()` and `fetchData()`; it has no heater-disable method. In sleep, the firmware sets `HCTRL` in register `0x70` and clears `RUN_GAS` in `0x71`, then reads both bits back. HP-354 setup re-enables the gas path using the unchanged Bosch parallel profile. The heater-off register behavior and thermal settling still require electrical verification.
- The first scan is due 10 seconds after boot. Subsequent scans are due 10 minutes after their start. The profile remains ID 354 with the original ten temperatures and multipliers. A scan ends at the first real step 9 or at a 60-second hard timeout, then turns the heater off. A 60-second cooling interval suppresses ambient frames; this is a provisional settling time, **not** a temperature correction or proof of thermal equilibrium. The longer idle interval does not reuse an earlier gas value: only a newly valid HP-354 step produces a gas frame, identified by its existing `SCAN`, `STEP`, and valid `SEQ` fields.
- The 20-second no-real-gas watchdog runs only in gas mode. Dummy `GASM_VALID=0` fields are not failures. T/H/P validity and gas-step validity use separate success/failure state. Three consecutive invalid real gas fields still enter reset/reinitialization and backoff. A 60-second timeout with no real gas result for at least 20 seconds enters that reset path; a timeout with recent real fields ends as an incomplete scan. No missing step is synthesized. During recording, valid raw steps remain stored even if their scan is incomplete; the existing STOPPED policy still ACKs without storing gas rows. Downstream analysis uses only ten-step fingerprints satisfying the existing `(nrf_boot, scan_seq, profile_id)` completeness rules. A missing final step may leave parallel mode running until the 60-second cap, so this session can contain more than one partial scan; it cannot run indefinitely.
- The forced-mode completion time, actual 2-second cadence under BLE load, 10-minute scan interval, scan duration, 60-second cooling adequacy and heater-off current must be measured on hardware. The reduced heater duty cycle is not expected to violate the existing Bosch parallel-profile API, but baseline stabilization and fingerprint comparability after the longer heater-off interval remain hardware validation items.

## Wire, gateway, and cloud

- Existing v2 `BID=...` and v3 `V=3,...STEP=...` gas frames are unchanged. Ambient telemetry is a distinct `ENV,BID=...,SEQ=...,MS=...,T=...,H=...,P=...` line, fragmented by the existing NUS 20-byte/newline transport. It contains no gas resistance or heater step. The optional `STAT` suffix `MODE=ENV|GAS|COOL|REC,EOK=0|1,GOK=0|1` reports the two paths; older STAT frames remain accepted.
- The ESP tracks the latest ambient frame independently of gas sequence continuity. Only the first valid frame and then at most one every 300,000 ms enters the existing ACK-gated queue/spool. The unchanged 120-byte CRC record uses schema 4 with unused gas/step fields zero internally; the HTTP JSON omits `g` and heater metadata. v2/v3 spool records and their replay format remain unchanged. A schema-4 history row is always saved to `EnvironmentHistory` when capture time is known, with capture-time session metadata if applicable; unknown time goes to `Unassigned`. `SensorData` is not reset or reclassified.
- The gateway does not create queue or spool records for two-second ambient telemetry. When no real data batch is pending, a five-second `samples:[]` health heartbeat publishes the latest volatile environment state through the existing POST/redirect/application-ACK path. A real data upload has priority and a successful data ACK postpones the next heartbeat by five seconds. Heartbeats do not start during another HTTP job, OTA/DFU, package upload or OTA maintenance request; a failed heartbeat is not spooled and waits five seconds after completion. OTA lease acquisition/release remains a separate request because it verifies cloud recording state.
- Apps Script keeps routine `IDLE + samples:[]` heartbeats off the spreadsheet after an initial locked device/session synchronization. Cache entries request a ten-minute TTL but may be evicted earlier; a miss makes only a 250 ms lock attempt and retries rather than waiting 20 seconds. Actual sample ingest, journal recovery, ACK high-water updates, recording Start/Stop and OTA lease state changes remain serialized by the original script lock. A dashboard recording-cache miss under contention is shown as `UNKNOWN`, with controls disabled, rather than guessed or failed as a whole request. Health age is increased by any server processing delay before `server_seen_at` is written.
- The dashboard polls every five seconds and keeps T/H/P in a fixed display position while state and age continue to identify stale data. A normal update is bounded by the non-overlapping HTTPS transaction plus the next page poll rather than the five-minute history interval. At most one heartbeat is in flight, so a transaction longer than five seconds naturally limits the start rate. An idle gateway and one open dashboard tab can each make up to about 17,280 requests/day. Google's [Apps Script quotas](https://developers.google.com/apps-script/guides/services/quotas) can change; actual account usage and latency require monitoring, especially with multiple devices or viewers.

## Manual rollout and remaining risks

Deploy the updated Apps Script project before the gateway, then the nRF node. Validate old v2/v3 ACKs and rows first. This task performs none of those deployments. Existing `SPOOL fault=1` must be diagnosed on the physical ESP and unacknowledged files backed up before firmware or partition changes; neither automatic format nor data deletion is a remedy. With a persistent spool fault, later 5-minute history rows can still fill RAM and be dropped explicitly. A BLE outage loses nRF telemetry before it reaches the ESP. The 5-minute history has ACK/replay after gateway receipt, but the latest 2-second display value is deliberately volatile.
